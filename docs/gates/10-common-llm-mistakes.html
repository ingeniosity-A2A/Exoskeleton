The 10 Common LLM Mistakes

A diagnostic key, operating instruction, and explicit deny list for each failure mode.

Mistake 01: The model structurally cannot do the job. Insufficient reasoning depth, knowledge cutoff mismatch, or simply not enough parameters for the domain.

No amount of prompt engineering fixes a capability gap. The system must match the model to the task before touching the prompt.

  • Deny: Forcing local parameter proxies past their structural limits.
  • Deny: Substituting prompt trickery for proper model selection.

Mistake 02: LLMs default to safe, thorough, complete, and conventional patterns. They expand solution space rather than constrain it.

Occam's razor demands subtractive prompting. The simplest solution that handles load-bearing cases must be stated explicitly against training distribution pull.

  • Deny: Completeness bias, effort signaling, and pleasing bias.
  • Deny: Unrequested mirror states, redundant error handling, and complexity proxies.

Mistake 03: The prompt doesn't constrain the model sufficiently. Silence is filled with default assumptions.

Non-requirements must be made explicit. Stating what does not need to survive removes justification for unwanted complexity.

  • Deny: Unstated implicit assumptions and unaddressed local vs. global constraint confusion.
  • Deny: Silent conflict resolution without an explicit constraint hierarchy.

Mistake 04: The model treats hard constraints as soft preferences, downgrading a MUST to a SHOULD under friction.

Explicit compliance tiers prevent silent degradation by establishing non-negotiable halt conditions.

  • Deny: Re-interpreting invariants to resolve a conflict.
  • Deny: Silent degradation of hard operational boundaries.

Mistake 05: Context degradation over long conversations where early constraints dilute and bad output becomes an input assumption.

Constraints must anchor both top and bottom of prompts, requiring fresh contexts and explicit state summaries at task boundaries.

  • Deny: Mid-session drift reverting to default assistant behaviors.
  • Deny: Operating from stale historical assumptions that no longer reflect reality.

Mistake 06: Accepting the first plausible solution without exploring alternatives, resulting in cascade assumptions.

Reasoning checkpoints must enforce alternative generation before selection to prevent local optimization errors.

  • Deny: Pattern-matching to training distributions instead of reasoning about actual systems.
  • Deny: Unchallenged cascade assumptions that amplify initial errors.

Mistake 07: Validating compilation instead of correctness, and failing to execute an adversarial pass.

Explicit verification steps and red-team critique passes must isolate failure modes before code emission.

  • Deny: Claiming validation without adversarial red-teaming.
  • Deny: Confusing syntax compilation with logical problem resolution.

Mistake 08: Expanding tasks beyond parameters, turning specific fixes into refactors and violating the complexity budget.

Explicit scope ceilings and non-requirement lists strictly constrain code mutation boundaries.

  • Deny: Introducing new abstractions “for future flexibility.”
  • Deny: Modifying execution areas outside the designated target schema.

Mistake 09: Losing the operating frame over long sessions and reverting to safe, conventional assistant defaults.

Mandate reinforcement at task boundaries ensures systemic constraint propagation across multi-agent handoffs.

  • Deny: Abandoning designated operational mandates for generic assistant behavior.
  • Deny: Dropping upstream constraints in downstream agent execution.

Mistake 10: Correct reasoning buried in verbose qualifications, hedged explanations, and unparseable delivery formats.

Few-shot before/after gotcha pairs replace abstract paragraphs to enforce direct, unhedged answers.

  • Deny: Burying decisions under caveats, qualifications, and prose.
  • Deny: Abstract format descriptions that fail to pattern-match reliably.
